# Спека: Improvement Pass 1

Единый проход улучшений MediaForge: исправление найденных багов, rollback, фоновый apply,
рефакторинг SessionDetailPage, инструменты качества frontend, визуальное обновление.

Исполнитель работает в ветке `improvement-pass-1` (от `main`), **один коммит на фазу**,
push в `main` запрещён — результат уходит на ревью.

## Глобальные правила (обязательны для каждой фазы)

- Соблюдать `AI_INSTRUCTIONS.md`: бизнес-логика в сервисах, доступ к БД через репозитории,
  `pathlib`, никаких заглушек и TODO в готовом коде, dry-run никогда не трогает файловую систему.
- После каждой фазы: `python -m pytest backend/tests -q` — все тесты зелёные (сейчас 265 passed);
  `npm run build` в `frontend/` — без ошибок.
- Новая логика (rollback, фоновый apply, утилиты frontend) покрывается тестами.
- Не добавлять новых runtime-зависимостей во frontend (dev-зависимости для фазы 5 — можно).
- Все пользовательские строки UI — на русском, через `frontend/src/i18n.ts` (добавлять ключи туда,
  а не литералы в компонентах, если строка используется более одного раза или видна пользователю).
- Alembic в этот проход **не входит** (отдельный PR позже). Существующий механизм миграций
  (`backend/scripts/init_db._apply_column_migrations`) не менять, кроме указанного в фазе 1.

## Фаза 2 — Rollback

`backend/app/services/rollback_service.py` — сейчас пустая заглушка, при этом `rollback_data`
уже пишется в `ApplyOperationLog` при apply.

**Модель данных.**
- В `ApplyRunStatus` добавить `ROLLED_BACK`; в `PlanStatus` добавить `ROLLED_BACK`;
  в `OperationStatus` добавить `ROLLED_BACK`.
- Новых таблиц не создавать. Записи об откате добавлять в `ApplyOperationLog` того же
  `apply_run` со статусом `ROLLED_BACK`.

**Сервис `RollbackService`** (`rollback_service.py`):
- `rollback_plan(plan_id: int, confirm: bool) -> PlanRollbackResult`.
- Предусловия: `confirm=True`; план в статусе `APPLIED` или `FAILED`; существует хотя бы один
  apply run. Откатывается **последний** apply run плана.
- Берём `ApplyOperationLog` этого run со статусом `DONE`, обрабатываем **в обратном порядке**:
  - `MOVE_FILE`: переместить файл из `rollback_data["to"]` обратно в `rollback_data["from"]`.
    Перед перемещением: файл-источник существует, целевой путь свободен, оба пути проходят
    валидацию принадлежности сессии (`validate_source_in_session` / `validate_target_in_session`
    из `backend/app/utils/path_safety.py` — направление проверок зеркальное apply).
  - `WRITE_TEXT_FILE` и `DOWNLOAD_FILE`: удалить созданный файл (`rollback_data["path"]`),
    только если путь проходит валидацию `validate_target_in_session` относительно target root
    сессии. Отсутствующий файл — не ошибка (уже удалён), логировать и продолжать.
  - `CREATE_DIR`: удалить директорию **только если она пуста** (`Path.rmdir()` в try/except).
    Непустая директория — не ошибка, пропустить.
- Ошибка на любом шаге MOVE_FILE — остановка отката, `apply_run.error_message` заполняется,
  статусы: apply run остаётся `FAILED`... нет — фиксируем так: при ошибке отката run получает
  статус `FAILED` с `error_message`, план остаётся в прежнем статусе. При полном успехе:
  run → `ROLLED_BACK`, план → `ROLLED_BACK`, соответствующие `PlanOperation.status` → `ROLLED_BACK`.
- Все действия отражаются записями в `ApplyOperationLog` (status `ROLLED_BACK` или `FAILED`).

**API** (`backend/app/api/routes/operation_plans.py`):
- `POST /operation-plans/{plan_id}/rollback`, тело `{"confirm": true}`, ответ `PlanRollbackResult`
  (схема по аналогии с `PlanApplyResult`). Ошибки предусловий → 400, план не найден → 404.

**Frontend:**
- В `PlanApplyPanel` для плана в статусе `APPLIED` или `FAILED` показывать кнопку
  «Откатить изменения» с confirm-модалкой (по образцу `ApplyConfirmModal`), после отката
  обновлять план/операции/apply runs. Статус `ROLLED_BACK` добавить в
  `frontend/src/labels.ts` (подпись «Откачено», тон `warning`) и `frontend/src/types.ts`.

**Тесты** (`backend/tests/test_rollback_service.py`):
- успешный откат MOVE_FILE + WRITE_TEXT_FILE + CREATE_DIR (файлы реально возвращаются, tmp_path);
- откат после частично упавшего apply (только DONE-операции откатываются);
- занятый целевой путь → откат останавливается, статусы корректны;
- уже удалённый NFO → откат продолжается;
- непустая директория не удаляется, откат успешен;
- предусловия: без confirm / план READY / план без runs → PlanApplyError-подобная ошибка.

## Фаза 3 — Фоновый apply с прогрессом

Сейчас `POST /operation-plans/{plan_id}/apply` выполняет все операции синхронно в запросе —
на больших планах это таймаут без прогресса.

- Endpoint меняется: проверяет предусловия (как сейчас, включая валидацию плана), создаёт
  `ApplyRun` со статусом `RUNNING`, переводит план в `APPLYING`, **коммитит** и возвращает
  `PlanApplyResult` немедленно. Само выполнение — `asyncio.create_task`, внутри задача открывает
  **собственную** сессию через `async_session_factory` (request-сессия к этому моменту закрыта).
- Защита от гонок: если план уже `APPLYING` — 409. Повторный apply APPLIED-плана — 400 (как сейчас).
- `ApplyService` разбить: `start_apply(plan_id, confirm)` (предусловия + создание run) и
  `execute_apply_run(apply_run_id)` (цикл операций; переиспользовать текущую логику).
  Прогресс (`done_operations`/`failed_operations`) коммитить после каждой операции, чтобы
  polling видел актуальные цифры.
- Rollback (фаза 2) оставить синхронным (откат обычно меньше и его простота важнее).
- **Frontend**: после запуска apply — polling `GET /operation-plans/{id}/apply-runs` каждые
  1–2 с, прогресс-бар «N из M операций», по завершении — итоговый статус и обновление секций.
  Прогресс-бар — обычный `<div>` с шириной в %, стили в `index.css` через токены (фаза 6).
- **Тесты** (`backend/tests/test_apply_service.py` дополнить): start_apply возвращает RUNNING run;
  execute_apply_run доводит план до APPLIED; конкурентный старт при APPLYING отклоняется;
  существующие тесты полного apply адаптировать (вызов start + execute последовательно).

## Фаза 6 — Визуальное обновление

Без новых зависимостей, только CSS + разметка. Всё через design-токены.

1. **Токены.** В начале `frontend/src/index.css` объявить CSS-переменные в `:root`:
   цвета фона/поверхностей/текста/границ, акцент (текущий `#1d4ed8`), semantic-цвета
   (success/warning/danger/info — взять из текущих бейджей), радиусы (6px/8px/12px),
   тени. Заменить захардкоженные значения по файлу на `var(--…)` — механически, без
   изменения внешнего вида светлой темы.
2. **Тёмная тема.** Переопределение токенов в `[data-theme="dark"]`. Палитра: фон `#0f172a`,
   поверхности `#1e293b`, текст `#e2e8f0`, границы `#334155`, акцент `#3b82f6`; semantic-цвета
   осветлить до читаемых на тёмном (контраст ≥ 4.5:1 для текста). Переключатель в
   `Layout.tsx` (иконка ☀/🌙), состояние в `localStorage` (`mediaforge-theme`), дефолт —
   `prefers-color-scheme`. Атрибут ставится на `<html>` до первого рендера
   (инлайн-скрипт в `frontend/index.html`, чтобы не мигало).
3. **Степпер pipeline.** Вместо плоского списка из 10 строк «шаг — бейдж» — компактный
   вертикальный степпер: кружок-индикатор (галочка/спиннер/точка/крестик) + название шага,
   соединительная линия, активный шаг подсвечен акцентом. Выполненные шаги сворачиваются
   в одну строку. Компонент `PipelinePanel.tsx` из фазы 4.
4. **Карточки фильмов.** В секции проверки (`CompactMediaItemRow` и вокруг): постер крупнее
   и с фиксированным соотношением 2:3, скруглением и фоном-заглушкой; заголовок — крупнее;
   бейджи и кнопки действий — в одну строку снизу; описание TMDB обрезать до 3 строк
   (`-webkit-line-clamp`) с раскрытием по клику. Список остаётся вертикальным (не сетка) —
   это ревью-интерфейс, но каждая карточка должна читаться как карточка, а не таблица.
5. **Длинные пути.** Утилита `frontend/src/utils/formatPath.ts`: сокращение середины пути
   (`D:\Скачаное\…\Фильмы`) при длине > 40 символов, полный путь в `title`. Применить в
   таблице сессий и шапке сессии. Покрыть vitest-тестом.
6. **Пустые состояния.** Для «Сессий пока нет» и пустых секций — центрированный блок:
   крупная иконка (emoji или inline-SVG), 1–2 строки текста, primary-кнопка следующего действия.
7. Проверить обе темы на страницах: список сессий, детали сессии, настройки, мастер настройки,
   статус. Ни один текст не должен терять контраст.
